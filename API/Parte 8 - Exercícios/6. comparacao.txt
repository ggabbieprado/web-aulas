Vetor em memória. Um vetor JavaScript vive apenas enquanto a página está aberta. Assim que o usuário recarrega a página ou fecha a aba, tudo o que foi armazenado nele desaparece. Ele não é compartilhado com outros dispositivos nem com outros usuários, e seu limite é basicamente a memória do navegador. A validação e as regras de negócio, quando existem, ficam só no lado do cliente, o que significa que qualquer pessoa com acesso ao console pode alterá-las. Por isso, o vetor é adequado para estado temporário de tela — por exemplo, guardar a lista de publicações recebida da API para renderizar os itens —, mas não serve como forma de armazenamento real.

localStorage. O localStorage já oferece persistência: os dados sobrevivem ao recarregamento e ao fechamento do navegador, porque ficam gravados no próprio dispositivo. Ainda assim, essa persistência é local e por navegador. Se o usuário abrir o site em outro computador, em outro celular ou até em outro navegador, não verá os dados. Dois usuários diferentes no mesmo computador também compartilham o mesmo armazenamento, o que pode ser indesejado. O limite é de aproximadamente 5 MB por origem, e tudo é armazenado como texto (por isso a necessidade de JSON.stringify e JSON.parse). As regras de negócio continuam no cliente, portanto sujeitas a manipulação. O localStorage é adequado para preferências locais e rascunhos — tema claro/escuro, último filtro usado, um formulário ainda não enviado —, não para dados que precisam ser confiáveis ou compartilhados.

API conectada a um banco de dados. Aqui os dados saem do navegador e passam a viver no servidor. Isso resolve três limitações das abordagens anteriores de uma só vez: os dados são persistentes (sobrevivem a recarregamentos, troca de dispositivo e reinício do servidor), são compartilhados entre todos os usuários e dispositivos que acessam a aplicação, e as regras de negócio ficam no servidor, onde não podem ser burladas pelo cliente. Além disso, a API permite implementar autenticação, autorização por usuário, controle de concorrência e auditoria — coisas impossíveis de garantir apenas no navegador. O limite de armazenamento deixa de depender do navegador e passa a depender da infraestrutura do servidor. Em contrapartida, exige backend, banco, deploy e tratamento de rede (latência, indisponibilidade, erros HTTP), o que justifica todo o cuidado com fetch, try/catch e verificação de resposta.ok que vimos na aula.

Síntese. O vetor é estado de tela: existe para a interface funcionar agora. O localStorage é cache local por navegador: útil para conveniências do usuário naquele dispositivo. A API com banco é a fonte da verdade: o lugar onde os dados realmente existem, valem para todos e podem ser confiados. A evolução do projeto da aula anterior para este é exatamente essa troca: sair de “salvar no navegador” e passar a “salvar no servidor”, mantendo no cliente apenas o que é efêmero.
